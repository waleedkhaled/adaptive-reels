# Performance of a vertical video feed on Expo SDK 57

Stay on expo-video 57.0.5 in Expo Go and build the feed as a core FlatList with native paging plus a fixed pool of 3 players made with createVideoPlayer(null) and re-pointed with replaceAsync (previous / current / next). Both Expo's own sdk-57 feed example and Bluesky's production feed (expo 57.0.24, expo-video ~57.0.4, RN 0.86.3) work this way. Because retrieval cards sit between reels, assign players by video ordinal (not list index) and mount a VideoView only for the active reel and its neighbours; on Android one player must never sit in two mounted VideoViews. The reels are already well suited (faststart confirmed, about 2 MB, 36 KB header), so with whole-file buffering and useCaching the next reel should start from memory and reviews from disk; audio is about 60% of each file and can be cut without re-rendering. The main risk I found: on Pixel 9/10 (Android 15+), exactly-30 fps video caps the whole app UI at 30 Hz, and the opt-out exists only in expo-video 58 (SDK 58 is in beta). react-native-video v7 is still beta and needs Nitro modules, so it cannot run in Expo Go; FlashList/LegendList recycling brings no benefit for one-page-at-a-time feeds. Nothing was measured on a device in this track, so all timing targets below are targets, not results.

## Recommendations

- **must**: Build the player layer as a pool of exactly 3 players: createVideoPlayer(null) three times, re-pointed with replaceAsync, never useVideoPlayer(source). Give each reel in the feed a running video ordinal k (cards do not count) and use pool[k % 3], so previous / current / next reels always hold different players even with retrieval cards between them. Keep a ref of each player's current source and call replaceAsync only when it differs. On activation: pause the other two, play the current one. On leaving a reel: pause and set currentTime = 0. Keep the pool alive across the Feed and Knowledge-map tabs (pause on blur, release only when the provider unmounts), and wrap blur-time player calls in try/catch. _Why:_ This is the pattern in Expo's sdk-57 example and in Bluesky's production feed on the same versions. Index-based assignment breaks once cards shift indices, and one player in two mounted VideoViews does not work on Android. Three prepared 720p players is the smallest pool that gives instant forward and back swipes while staying clear of device-dependent decoder limits. Avoiding release on blur sidesteps open iOS issue #30994 with Expo Router.
- **must**: Use core FlatList, not FlashList, LegendList or pager-view. Settings: pagingEnabled; item height taken from the list container's onLayout (not Dimensions); getItemLayout = {length: h, offset: h * index, index}; windowSize 5; initialNumToRender 2; maxToRenderPerBatch 2; removeClippedSubviews false; showsVerticalScrollIndicator false; a module-level viewabilityConfig {itemVisiblePercentThreshold: 60, minimumViewTime: 0} with a stable onViewableItemsChanged; keyExtractor on the feed-slot id; memoised cells that receive only active and adjacent booleans. If Android paging lets fast flicks skip a page, switch to snapToInterval = h, snapToAlignment 'start', disableIntervalMomentum, decelerationRate 'fast'. _Why:_ Only one to three full-screen cells are ever mounted, so recycling buys nothing and adds state-reset hazards for video cells and mixed item types (issue #40376). FlatList with native paging is what Bluesky ships on RN 0.86.3. A 60% threshold starts playback mid-swipe; Bluesky uses 100% (play after the page settles) and Expo's example uses 50%. pager-view mounts all children and would need hand-rolled windowing.
- **must**: Mount a VideoView only where it is needed: on iOS for the active reel and its two neighbouring reels; on Android start with the active reel only, then try neighbours on your test phone. Every other mounted cell renders a placeholder. VideoView props: nativeControls false, contentFit 'contain', allowsVideoFrameAnalysis false, surfaceType left at the default. Put a static gradient (#0B1220 to #13213D) behind the VideoView and make every reel open with about 300 ms of that plain background, so the placeholder-to-video handoff is invisible. Add an Android watchdog: if currentTime has not advanced 1 s after play(), call replaceAsync with the same source or remount the VideoView with a new key. _Why:_ Decoupling VideoView mounting from windowSize guarantees no player is in two views. Active-only on Android is Bluesky's production setting. 'contain' avoids cropping lesson text on 19.5:9 phones and avoids the documented Android overlapping-cover bug. The watchdog covers open issue #39962, where the view stays black although onFirstFrameRender fires. Because all reels share one background, no per-reel poster images are needed.
- **must**: Set player options explicitly when the pool is created. bufferOptions as one object: {preferredForwardBufferDuration: 40, minBufferForPlayback: 0.5, waitsToMinimizeStalling: true}. loop false, with the playToEnd event as the completion signal and a replay as the rewatch signal. timeUpdateEventInterval 0.25 on iOS and 0.5 on Android for the active player only, 0 on the others. Feed progress into a ref or shared value, not screen-level state. _Why:_ Reels are at most 37 s and about 2 MB, so a 40 s forward buffer makes each preloaded player hold the whole file (about 6 MB across the pool) and, with caching on, writes the full reel to disk. Docs and sdk-57 source disagree on Android defaults, so explicit values remove the doubt. 0.5 s to start shortens non-preloaded starts. Bluesky found Android cannot keep up with short timeUpdate intervals. A per-tick setState at screen level would re-render the list during playback.
- **must**: Turn on useCaching: true for every reel source and keep expo-video at 57.0.5 or later. Leave the cache at the 1 GB default. Add a small file prefetch queue with expo-file-system (File.downloadFileAsync into Paths.cache, idempotent, 2 at a time) for the reels the agent ranks N+2 and N+3 plus the top candidate of each other pool, and play the file:// URI when the file exists. Before a demo, pre-download the reels of the selected topics. The static host for the tester build must send Content-Length and support Range requests. _Why:_ The whole library (256 MB) fits in the default cache, and reviews of earlier concepts then start from disk and work offline. The iOS cache crash fixes only landed in 57.0.5, and iOS caching fails without Content-Length. The 3-player pool only covers N+1; files on disk make a re-planned next reel cheap to swap in and make the 3-minute demo independent of venue Wi-Fi. The speed of a file:// start was not measured.
- **must**: Before recording or showing the demo on Android, check for the 30 Hz cap: play a reel and run adb shell dumpsys SurfaceFlinger | grep -E "requestedFrameRate|FrameRateOverrides". If the video layer votes 30 Hz, try surfaceType 'textureView' on Android and re-check; if that does not help, either demo on an iPhone or a non-adaptive-refresh Android, or move to SDK 58 when stable and pass {videoChangeFrameRateStrategy: 'off'} as the second argument of createVideoPlayer. _Why:_ Our reels are exactly 30 fps, which is the trigger described in PR #47873, and expo-video 57 has no opt-out. Whether textureView avoids the frame-rate vote is my untested assumption (the PR only tests surfaceView). The dumpsys check is the PR's own verification step and takes a minute.
- **should**: Define the agent-to-player contract around preloading: when reel N becomes active, commit N+1 and preload it; apply watch-behaviour signals from N (completion, early skip) from N+2 onward. For the explicit quick actions ('More like this', 'Too easy', 'Not for me'), re-plan N+1 immediately and call replaceAsync on the next player while the learner is still on N. Treat a retrieval card as a non-video slot that leaves the previous and next reel players untouched. _Why:_ A preloaded neighbour is what makes the swipe instant, so the next item cannot be chosen at swipe time. Quick actions happen while the current reel is still on screen, which leaves time to re-buffer a 2 MB file, so the demo can still show the feed adapting on the very next swipe. An early skip is the one signal that arrives too late for N+1.
- **should**: Shrink the reels without re-rendering: ffmpeg -i in.mp4 -c:v copy -c:a aac -b:a 96k -movflags +faststart out.mp4. At the next full re-render, also output limited-range yuv420p with bt709 tags instead of yuvj420p, and keep frame 0 a keyframe. _Why:_ Audio is about 317 kbps of a 513 kbps file; 96 kbps is ample for speech and takes a reel from about 2.0 MB to about 1.2 MB, which cuts prefetch time and data by roughly 40%. Full-range yuvj420p may decode with slightly different levels on some Android hardware decoders, which would show as a colour step against the gradient placeholder; I have not tested this on a device.
- **should**: Instrument from day one and measure in production mode (npx expo start --no-dev --minify). Per swipe, log: time from cell activation to onFirstFrameRender, whether player.status was 'readyToPlay' at activation, and the source type (memory, disk, network); add performance.mark/measure so they show in the React Native DevTools Performance panel. On Android use adb shell dumpsys gfxinfo host.exp.exponent and dumpsys meminfo. Targets to hold: preloaded swipe to first frame at most 100 ms median and 250 ms p95 on iOS, at most 250 ms median on Android with active-only mounting; preload hit rate at least 90%; non-preloaded start on Wi-Fi at most 600 ms median; at least 55 fps during swipes on iPhone and 50 on a mid-range Android with no frozen frames (over 700 ms); memory flat within about 20 MB over 50 swipes with exactly 3 players alive. _Why:_ Expo's docs state the app runs slower in development mode, so dev-mode numbers mislead. The 'ready at activation' flag is Bluesky's way of separating load time from swipe latency. The targets are my engineering targets, set from the self-reported reference numbers (about 0-5 ms perceived start, about 55 fps) and Android's slow/frozen frame definitions; none were measured for this app. Native profilers cannot attach to the store build of Expo Go on iOS, so deeper profiling waits for the EAS dev build.
- **could**: Do not switch to react-native-video v7 for this demo. Revisit it only if, after the EAS dev build exists, you need what expo-video lacks: a native preload window deeper than one item, DRM, ads or its offline download plugin. Plan the SDK 58 upgrade once it is stable. _Why:_ v7 is beta (7.0.0-beta.11) with a stated risk of breaking changes and needs Nitro modules, so it cannot run in Expo Go. SDK 58's expo-video brings the frame-rate strategy option, useVideoPlayer switching to replaceAsync, and reduced iOS main-thread load when loading videos. With 2 MB progressive MP4s and one committed next item, expo-video's 3-player model is sufficient.

## Fact-check: changes to the recommendations

- Raise the SDK 58 item from 'could, once stable' to 'must, schedule inside M3'. Stable is expected around 2026-10-06 to 10-13, and the store Expo Go then drops SDK 57. Either upgrade when stable, or accept staying on 57 through a sideloaded Android Expo Go, 'eas go' (needs a paid Apple Developer membership) or a dev build. Upgrading brings videoChangeFrameRateStrategy 'off', the iOS source-loading race fix and reduced iOS main-thread load.
- 30 Hz cap: 'demo on an iPhone' is not a full answer, because PLAN.md makes an Android APK the first tester channel. Add a content-side option that works on SDK 57: render or re-encode the reels at 60 fps (pipeline/src/config.ts and the hard-coded 30 in render/remotion/Root.tsx). By the PR's own mechanism the cap should then be 60 Hz instead of 30; this is untested, so verify with the dumpsys check. Keep textureView as the second option.
- Change loop to true. Count loops from playToEnd (it fires on every loop on both platforms), read player.currentTime when the reel is left to get watched_ms, and derive Completed (>= 90%), Rewatch (extra loop >= 50%) and Early skip as PLAN.md defines them. Do not use playToEnd as the completion signal.
- On SDK 57, serialise replaceAsync per player: await the previous call or use a generation token and ignore stale completions. The fix for overlapping source loads on iOS (#47967) is 58-only, and the 'quick action re-plans N+1 immediately' rule creates exactly those overlapping loads.
- Stop citing Bluesky as proof for the null + replaceAsync + useCaching + 40 s buffer design; it uses sync replace(), HLS, no caching and default buffers. Keep the design (Expo's example and docs back replaceAsync), but make 'three pooled players with progressive MP4, useCaching and whole-file buffering' the first thing tested on both platforms in M3.
- Use one disk mechanism per reel, not two: either a prefetched file:// copy or useCaching on the URL. Track each player's current source by reel id, not URI, because the URI changes between http and file://.
- Fix the prefetch queue: check file.exists before downloading, since idempotent: true overwrites rather than skips. Download to a temporary name and move it into place, so a truncated file is never played.
- Performance targets: use PLAN.md's M3 acceptance ('prefetched reels start in under 500 ms') as the pass line and treat 100 ms / 250 ms as stretch goals. The '55 fps' reference figure is a JS requestAnimationFrame count from react-native-video v7 beta.2 on unnamed devices; measure UI frames with gfxinfo instead.
- Keep core FlatList, but change the rationale: Expo's own PR found FlashList 'slightly smoother'. The reasons to choose FlatList are parity with Bluesky's production feed and the mixed-item freeze report (#40376), not that recycling has no benefit.
- Keep the Android black-frame watchdog as a must and do not expect SDK 58 to remove it: the upstream Media3 issue (androidx/media#2809) is still untriaged.

## Fact-check: what the track missed

- Expo Go on iOS now requires being logged in to the same Expo account in both Expo CLI and the app (changelog 2026-09-03, applies to the App Store version that added SDK 57). The demo phone and any tester phone need this set up beforehand; development builds do not.
- Expo Go's store version has been fragile this year: SDK 55 sat in App Store review, and Expo now describes Expo Go as 'first and foremost an educational tool' and steers other uses to development builds. Combined with the SDK 58 flip expected in mid-October, an EAS dev build should be planned early rather than left to M7.
- SDK 58 removes InteractionManager (the post says to use requestIdleCallback) and ships React Native 0.88 with the Strict TypeScript API as default. Do not build 'defer agent work until after the swipe' on InteractionManager.
- On SDK 57 a VideoView keeps a strong reference to its VideoPlayer after detach (fixed in 58, #46453). With pooled players moving between cells this can skew the 'memory flat over 50 swipes' target; measure it on 57 and again after the upgrade.
- iOS audio default differs by SDK: sdk-57 source has audioMixingMode = .doNotMix, and 58 changes the default to auto. Set audioMixingMode explicitly so behaviour does not change on upgrade. PLAN.md's 'audio never overlaps' acceptance also needs pause-before-play ordering across the three players.
- The reels are tagged BT.601 (color_space bt470bg) as well as full range, although the pipeline requests pixelFormat 'yuv420p'. If the design system triggers a re-render anyway, fix range and colour tags and consider 60 fps in the same pass.
- The plain-HTTP media server works in Expo Go, but I did not verify that an EAS APK or iOS internal build will load http:// URLs; release builds commonly block cleartext. Check this before M7 or serve the tester library over HTTPS.
- Captions appear to be burned into the reels (Reel.tsx animates word timings), so the app needs timeUpdate events only for a progress bar. watched_ms can come from player.currentTime at deactivation, which lets timeUpdateEventInterval stay at 0 if no progress bar is shown.
- Process note: the Expo docs markdown pages include a block telling AI agents to submit feedback to api.expo.dev. I did not act on it. The docs/source mismatch on Android buffer defaults is real if you want to report it yourself.

## Findings

### 1. expo-video 57 separates VideoPlayer from VideoView; preloading means creating a player with a source before it has a view. Deferred preloading is a null-source player plus replace. replace() blocks the iOS main thread, so replaceAsync is the method to use. Players from createVideoPlayer must be released by hand.

Docs v57: "Even when the player is not connected to a VideoView, it will fill the buffers." For later preloading, create a player with a null source and replace it. replace(): on iOS it "loads the asset data synchronously on the UI thread" and "will be deprecated"; replaceAsync offloads loading. createVideoPlayer "doesn't release automatically"; release() is the caller's job. VideoView.player accepts null. onFirstFrameRender is documented for hiding cover images.

Source: <https://docs.expo.dev/versions/v57.0.0/sdk/video/> · confidence: high · version-sensitive

### 2. In expo-video 57.0.5, useVideoPlayer destroys and re-creates the native player whenever its source argument changes. SDK 58 changes this to replaceAsync. On SDK 57, never pass a changing source to the hook.

sdk-57 source: useVideoPlayer calls useReleasingSharedObject(() => new NativeVideoModule.VideoPlayer(...), [JSON.stringify(parsedSource), JSON.stringify(playerBuilderOptions)]). The 58.0.0 changelog lists "When source of useVideoPlayer changes use replaceAsync instead of re-creating the player (#46495)". Expo's FlashList example comments that re-creating the player on item change "is slow" and passes null instead.

Source: <https://raw.githubusercontent.com/expo/expo/sdk-57/packages/expo-video/src/VideoPlayer.tsx> · confidence: high · version-sensitive

### 3. Expo's official feed example on the sdk-57 branch uses FlatList plus a fixed pool of createVideoPlayer(null) players indexed by index % pool, with replaceAsync per cell. The pool size (10) matches the number of mounted cells (windowSize 10).

VideoFlatListScreen.tsx: createPlayerPool(10) with bufferOptions {preferredForwardBufferDuration: 5}; FlatList with snapToInterval = measured height, disableIntervalMomentum, decelerationRate 0.8, initialNumToRender 1, maxToRenderPerBatch 1, windowSize 10, removeClippedSubviews false, viewability itemVisiblePercentThreshold 50; VideoView with nativeControls false, contentFit contain, allowsVideoFrameAnalysis false; players released in effect cleanup. PR #33129 (merged Dec 2024) says people fail "because they create too many players or create a new player every time the source changes".

Source: <https://raw.githubusercontent.com/expo/expo/sdk-57/apps/native-component-list/src/screens/Video/VideoFlatListScreen.tsx> · confidence: high · version-sensitive

### 4. Bluesky's production vertical video feed runs on our exact stack and uses exactly 3 pooled players (previous / current / next by index % 3) in a FlatList with pagingEnabled. On Android it mounts a VideoView only for the active item.

package.json: expo 57.0.24, expo-video ~57.0.4, react-native 0.86.3. VideoFeed/index.tsx: createThreeVideoPlayers via createVideoPlayer; a source is replaced only when it differs from the one tracked for that player; List (FlatList) with initialNumToRender 3, maxToRenderPerBatch 3, windowSize 6, pagingEnabled, viewability itemVisiblePercentThreshold 100 / minimumViewTime 0; shouldRenderVideo = active || ios(adjacent); on Android the VideoView stays at opacity 0 until timeUpdate reports currentTime >= 0.05; timeUpdateEventInterval 0.2 iOS / 0.5 Android ("android is typically slower"); players released when the screen loses focus; telemetry records whether player.status was readyToPlay at activation.

Source: <https://raw.githubusercontent.com/bluesky-social/social-app/main/src/screens/VideoFeed/index.tsx> · confidence: high · version-sensitive

### 5. There is no fixed Android limit on concurrent players: hardware video decoder instances depend on the device, the content and what other apps hold at that moment. This is why a small fixed pool is the safe design.

Media3 maintainer (marcbaechinger) on androidx/media#1880: "It depends on many factors and specifically on the device"; an app shares codec resources with other apps; audio codecs are software and less constrained. Android reference for getMaxSupportedInstances(): "a hint for an upper bound... the actual number of concurrently operable instances may be less". expo-video's Android player enables decoder fallback (setEnableDecoderFallback(true)) and builds one ExoPlayer plus MediaSession per VideoPlayer.

Source: <https://github.com/androidx/media/issues/1880> · confidence: high

### 6. On Android, one VideoPlayer cannot be shown in two mounted VideoViews, and SurfaceView (the default) is the right surface for a scrolling feed on current Android. textureView is only needed for the documented overlapping contentFit=cover bug.

expo docs: "mounting multiple VideoView components at the same time with the same VideoPlayer instance will not work due to a platform limitation" (issue #35012, labelled upstream ExoPlayer). Known issue: two overlapping VideoViews with contentFit cover may draw out of bounds; workaround surfaceType textureView. Android Media3 surface page: SurfaceView gives "significantly lower power consumption" and "more accurate frame timing"; it was not synchronised with scrolling only before Android 7.0 (API 24).

Source: <https://developer.android.com/media/media3/ui/surface> · confidence: high

### 7. On adaptive-refresh Android phones (Pixel 9/10, Android 15+), an exactly-30 fps video in a SurfaceView caps the whole app UI, including the swipe animation, at 30 Hz. expo-video 57 has no opt-out; the option exists only from 58.0.0. Our reels are exactly 30 fps.

PR #47873 (merged to main 2026-07-27): ExoPlayer's default strategy calls Surface.setFrameRate(contentFps); "the pager animates at 30 fps on a 120 Hz panel"; observed on Pixel 10 Pro, Android 16, expo-video 56.1.4. It adds PlayerBuilderOptions.videoChangeFrameRateStrategy ('off' | 'onlyIfSeamless'). The sdk-57 PlayerBuilderOptions.kt has only the two seek-increment fields, and the sdk-57 changelog shows no backport. ffprobe on our reels reports r_frame_rate=30/1.

Source: <https://github.com/expo/expo/pull/47873> · confidence: high · version-sensitive

### 8. bufferOptions must be set as one whole object, and the documented Android defaults (20 s forward buffer, 2 s minimum to start) do not match the sdk-57 native constants (50 s, 1 s). Set the values explicitly rather than relying on defaults.

Docs: "Setting individual buffer properties is not supported"; preferredForwardBufferDuration default "Android: 20, iOS: 0"; minBufferForPlayback default 2. sdk-57 DefaultLoadControl.java: DEFAULT_MIN_BUFFER_MS = DEFAULT_MAX_BUFFER_MS = 50_000, DEFAULT_BUFFER_FOR_PLAYBACK_MS = 1000, after rebuffer 2000; BufferOptions.kt defaults to these and they are applied only when JS sets bufferOptions. VideoPlayerLoadControl sets min and max buffer both to preferredForwardBufferDuration. iOS defaults: preferredForwardBufferDuration 0 (automatic), waitsToMinimizeStalling true.

Source: <https://raw.githubusercontent.com/expo/expo/sdk-57/packages/expo-video/android/src/main/java/expo/modules/video/player/DefaultLoadControl.java> · confidence: medium · version-sensitive

### 9. Disk caching is opt-in per source (useCaching: true), persistent, LRU with a 1 GB default, and works offline for progressive MP4 on both platforms. The iOS cache had two crash bugs that are fixed only from expo-video 57.0.5.

Docs: default cache 1GB, evicted least-recently-used; cached portions play offline; no HLS caching on iOS; setVideoCacheSizeAsync and clearVideoCacheAsync "can be called only if there are no existing VideoPlayer instances". sdk-57 changelog 57.0.5 (2026-09-24): fixed a data race in the iOS cache's open-file registry and a crash when storage runs out while writing the cache. Issue #43957: iOS caching fails for servers that reply chunked without Content-Length. Android uses Media3 SimpleCache with LeastRecentlyUsedCacheEvictor (1 GB).

Source: <https://raw.githubusercontent.com/expo/expo/sdk-57/packages/expo-video/CHANGELOG.md> · confidence: high · version-sensitive

### 10. A feed that mixes video and non-video items with a 3-player pool froze on Android in a public bug report, and it was closed as stale with no maintainer diagnosis. Our feed has the same shape (reels plus retrieval cards). Two other relevant issues are still open.

expo/expo#40376 (SDK 54, FlashList, 3-player pool): the player freezes at about item 10 only when white non-video items are mixed in; an all-video list works; the reporter says FlatList with default settings was worse; closed by the stale bot 2026-01-30. My reading (not confirmed by Expo): with index-based pooling and many mounted cells, one player ends up in several mounted VideoViews, which Android does not support. Open: #39962, Android VideoView sometimes stays black although onFirstFrameRender fires (about 5% on emulator, rarer on devices, upstream ExoPlayer); #30994, iOS 'shared object cannot be found' when a player is manipulated in an Expo Router blur listener.

Source: <https://github.com/expo/expo/issues/40376> · confidence: medium · version-sensitive

### 11. For full-screen paging, FlatList's relevant controls are windowSize (in viewport units, default 21), getItemLayout, and removeClippedSubviews (default true on Android, with a missing-content warning). FlashList v2 is JS-only and New-Architecture-only, but its value is cell recycling, which does not help when one to three cells are mounted.

RN docs: windowSize "1 is equivalent to your viewport height. The default value is 21"; getItemLayout "removes the need for your FlatList to manage async layout calculations"; removeClippedSubviews "can have bugs, such as missing content". ScrollView docs: snapToInterval overrides pagingEnabled; disableIntervalMomentum stops on the next index; decelerationRate 'fast' = 0.99 iOS / 0.9 Android. FlashList README: "JS-only solution in v2: No native dependencies", "new architecture only"; its docs say snap/paging ScrollView props pass through but are not documented, minimumViewTime defaults to 250 ms, and maintainVisibleContentPosition is on by default.

Source: <https://reactnative.dev/docs/optimizing-flatlist-configuration> · confidence: high

### 12. The SDK 57 module set pins expo-video ~57.0.5, gesture-handler ~2.32.0, reanimated 4.5.1, worklets 0.10.1, pager-view 8.0.2 and flash-list 2.0.2. react-native-video v7 is still beta and needs react-native-nitro-modules, which is not in that set, so it needs a dev build.

sdk-57 bundledNativeModules.json lists those versions and contains no nitro or react-native-video entry. npm on 2026-10-04: react-native-video latest 6.19.3, beta 7.0.0-beta.11 (2026-08-12) with peer dependency react-native-nitro-modules >= 0.35.0; expo-video latest 57.0.5, next 58.0.6; flash-list latest 2.3.3; @legendapp/list 3.6.0. The v7 README says it is "in active development. You can expect breaking changes and missing features." The SDK 57 changelog says expo@57.0.9 fixes a Hermes V1 memory regression for apps using reanimated/worklets (the repo is on ~57.0.26). SDK 58 beta was announced 2026-09-15.

Source: <https://raw.githubusercontent.com/expo/expo/sdk-57/packages/expo/bundledNativeModules.json> · confidence: high · version-sensitive

### 13. Public reference feeds preload 1 behind and 3 to 5 ahead and report near-zero perceived start time when the preload succeeds. These are vendor self-reported numbers with no devices named.

TheWidlarzGroup react-native-video-feed (react-native-video 7.0.0-beta.2, LegendList, Expo 52, RN 0.76): preload ahead 3 on Android / 5 on iOS, 1 behind; draw distance 2x / 3x item height; viewability threshold 30%; reported "~19ms" TTFF, "~0-5ms" perceived TTFF, "~55 fps", "<5ms" scroll lag. It measures TTFF from replaceSourceAsync/preload to readyToPlay and perceived TTFF from visibility to readyToPlay. Mux's expo-video feed uses FlashList, 5 ahead / 1 behind, and null sources outside the window. Google's Media3 preload example loads 5 s for the next item and 3 s for the previous.

Source: <https://sdk.thewidlarzgroup.com/video-feed> · confidence: medium · version-sensitive

### 14. Our rendered reels are already fast-start and tiny, but audio is about 60% of each file, the pixel format is full-range yuvj420p, and the local media server already supports byte ranges.

ffprobe plus an MP4 atom walk on the local library (119 files, 256 MB on disk): H.264 High@3.1, 720x1280, 30 fps, yuvj420p; video about 180-260 kbps; AAC-LC 48 kHz stereo about 317 kbps; total about 513 kbps, 1.7-2.4 MB per reel; atom order ftyp, moov (about 36 KB), mdat in all 6 sampled files; keyframes in one sample at 0, 8.3, 14.8 and 23.1 s. pipeline/src/serve.ts answers Range requests with 206, Content-Length and Accept-Ranges. There is no poster image per reel.

Source: <file://library/reels/rn-expo-workflow--example/video.mp4> · confidence: high

## Open questions

- Which phones will run the demo? An iPhone avoids the Android-only risks. A Pixel 9/10 needs the 30 Hz check, and a mid-range Android needs the 3-player pool and the VideoView-per-neighbour option tested early.
- Does surfaceType 'textureView' actually avoid the 30 Hz frame-rate vote on expo-video 57? I could not find a primary source; it needs the dumpsys test on an adaptive-refresh device.
- How long does a non-preloaded start take with replaceAsync from a file:// URI, from the LAN server and from the static host? No source gives expo-video numbers and nothing was measured here; this decides how freely the agent may re-plan N+1.
- Do three prepared ExoPlayers each hold a hardware decoder while not attached to a surface on the target Android phone? I believe so (ExoPlayer uses a placeholder surface) but did not verify it in the Media3 source or on a device.
- The root cause of issue #40376 (mixed video and non-video items freezing on Android) was never diagnosed by Expo. The video-ordinal pooling and limited VideoView mounting should avoid my suspected cause, but a mixed reel-plus-card feed must be tested on Android in the first M3 build.
- SDK 58 is in beta since 2026-09-15. When it goes stable the store version of Expo Go will move to it, which may force the upgrade mid-project; I did not find a release date.
- Does full-range yuvj420p show a visible colour or brightness step against the RN-drawn gradient on Android hardware decoders? Untested.
- Should waitsToMinimizeStalling be false on iOS for local or cached sources to start sooner? Left at the default; worth an A/B on device.
- I could not open the LegendList docs (404), so its fit for paging is judged only from TheWidlarzGroup's repo and npm metadata.
- The Expo docs and the sdk-57 source disagree on Android buffer defaults (20 s / 2 s vs 50 s / 1 s). The docs page carries an embedded note asking AI agents to submit feedback to Expo; I did not send anything. You may want to report it yourself.
