# App-level performance on React Native 0.86 / Expo SDK 57

On Expo SDK 57 / RN 0.86 the engine and architecture are already settled (Hermes V1 is the default, New Architecture only), so this app's performance comes down to a few app-level choices. Those are: enable React Compiler, keep learner state in one external store with narrow selectors, run Reanimated 4.5 animations on transform/opacity, use a JS-only recycling list for the feed, and keep persistence off the swipe path with expo-sqlite's async API in WAL mode. Everything the demo needs runs in Expo Go (Reanimated 4.5.1, FlashList 2.0.2, expo-sqlite, expo-file-system, expo-image, expo-video); the things that do not are react-native-mmkv v4, Reanimated static feature flags, embedded fonts and a faithful splash screen. Native lazy route loading has no effect in production, so startup work is about a light root layout, a cached manifest and hiding the splash early. Dev-mode numbers are not representative: measure with `npx expo start --no-dev --minify` for quick checks and an EAS release build for acceptance, because local Xcode 26.0 cannot build SDK 57. Targets the sources give are 16.67 ms per frame at 60 fps, Android's "excessive" cold start at 5 s or more, and Apple's 400 ms to first frame; the agent budget (2 ms per call) and persistence latencies are my own proposed targets and are unmeasured.

## Recommendations

- **must**: Take every performance number in production-mode JS on a real phone and write the budgets into the M7 'performance pass'. Use `npx expo start --no-dev --minify` in Expo Go for quick checks and an EAS release (preview/internal) build for acceptance. Budgets: 16.67 ms per frame (8.33 ms on 120 Hz phones) with no dropped UI frames during a swipe; cold start to first reel poster at most 2 s (my target; Android flags 5 s or more as excessive, Apple aims for 400 ms to first frame); prefetched reel start under 500 ms (already in PLAN M3). Strip or guard console.log in production. _Why:_ RN, Expo, FlashList and Reanimated docs all say dev mode distorts results (Android debug about 20 FPS vs 60 optimised). Local Xcode 26.0 cannot build SDK 57, so EAS is the only route to an iOS release build. Expo Go startup is not representative because it does not run precompiled bytecode.
- **must**: Add `"experiments": { "reactCompiler": true }` to apps/mobile/app.json now, before feed code is written, and keep the eslint-config-expo compiler rules on. Do not hand-write useMemo/useCallback/memo by default; use sharedValue.get()/set() instead of .value in Reanimated code. _Why:_ The SDK 57 default template ships with it enabled and Babel is preconfigured; the repo's app.json lacks the flag. Turning it on at M3 costs nothing, whereas retrofitting later means fixing Rules-of-React violations across finished screens.
- **must**: Hold learner state, the planned queue and the active reel id in one Zustand 5 store as the in-memory source of truth. Subscribe with narrow selectors that return primitives or stable references: per reel cell `s => s.activeId === id`, per map cell `s => s.mastery[conceptId].box`. Make the agent's returned state share structure (replace only the changed concept entries). Keep playback position and watch-time out of React state (player events into refs or shared values) and write them to the store only at swipe end. _Why:_ Zustand 5 re-renders purely on selector output via useSyncExternalStore and loops on fresh references. With structural sharing, a swipe re-renders two cells and an answer re-renders one map cell rather than all 40, which is what makes the map visibly fill in without jank.
- **must**: Give the selection agent an explicit budget and instrument it: at most 2 ms p95 per next() call and at most 5 ms for re-planning the 2-3 prefetch slots, measured in release. Call it after the swipe settles, never inside a scroll handler. Build lookup indices once at manifest load (prerequisites, RELATED_TO neighbours and reels per concept as Maps/arrays). Wrap calls in performance.mark/measure, add a Vitest bench in packages/agent, and log longtask entries in tester builds. Keep Zod validation to a single pass at manifest load. _Why:_ The graph is tiny (46 nodes, 105 edges, 119 reels), so the agent should be far below the budget, but Hermes V1 has no JIT and the budget figures are my proposal, not measured. User Timing and PerformanceObserver are stable since RN 0.83 and work in production, so the check is cheap to keep permanently.
- **must**: Use one expo-sqlite database for persistence: run `PRAGMA journal_mode=WAL; PRAGMA synchronous=NORMAL` at open; append events through a prepared statement with the async API and never call *Sync methods on the swipe path; store learner state as one JSON snapshot row written at most about once per second plus on app background; hydrate once at startup with a single synchronous read before hiding the splash. Generate the JSONL export on demand from the events table with the File API. Skip MMKV. _Why:_ expo-sqlite is in Expo Go and its async calls keep disk I/O off the JS thread; File.write append and the kv-store sync setters block the JS thread, and the kv-store does not set WAL. WAL with NORMAL avoids a sync on most commits at the cost of possibly losing the last events on power loss, which is acceptable for a demo. MMKV v4 needs Nitro and a prebuild, and the data here is a few KB.
- **should**: Install animation libraries with `npx expo install` so they stay at Reanimated 4.5.1 / worklets 0.10.1. Use CSS transitions with explicit properties (never 'all') for state-driven UI: the why-this-reel chip, map cell colour fill, card feedback. Use worklets with Gesture Handler only for gesture-driven motion. Animate only transform, opacity and backgroundColor, and keep animated components on screen under about 100. Do not depend on Reanimated static feature flags while on Expo Go. _Why:_ This follows Reanimated's own guidance and limits; 40 map cells fit comfortably. Expo Go ships Reanimated prebuilt with default flags, and a newer npm version (4.7.x) would not match Expo Go's native side.
- **should**: Build the feed on FlashList v2 with pagingEnabled, a stable keyExtractor, getItemType for 'reel' vs 'card', no `key` props inside item components, and a small data window (previous, current, next 2-3 planned). Render the 40-cell knowledge map with plain Views and no virtualisation. Judge list performance only in release mode; fall back to FlatList with windowSize 3 if cell recycling conflicts with expo-video player lifecycle. _Why:_ FlashList v2 is JS-only (works in Expo Go), built for the New Architecture and needs no size estimates. Because the agent produces items one at a time, the mounted window is tiny, so correctness of recycling with video players matters more than raw list throughput.
- **should**: Keep startup short: a light root layout; SplashScreen.preventAutoHideAsync() at module scope and hide() as soon as the profile is hydrated and the first item is chosen; cache the manifest locally so launch never waits on the network; use system fonts while on Expo Go and switch to the expo-font config plugin in the EAS build; wrap the dashboard graph in React.lazy only if it imports a heavy library (Skia, d3). Do not spend time on asyncRoutes for native. _Why:_ Native production loads all routes synchronously and bytecode is memory-mapped, so the real costs are module initialisation, manifest parsing and waiting on I/O. Embedded fonts remove an async load but are unavailable in Expo Go. The reel look is a Helvetica-style sans, which system fonts already match.
- **should**: Use expo-image for reel posters and thumbnails: have the pipeline emit a poster and a ThumbHash per reel, call Image.prefetch on the posters of the next 2-3 planned reels with 'memory-disk', set recyclingKey to the reel id in recycled cells, and keep the cross-fade at or under about 150 ms. _Why:_ A cached poster gives an instant first frame while the player becomes ready, which protects the under-500 ms start target; recyclingKey prevents a recycled cell from flashing the previous reel's poster.
- **could**: Once per milestone run `EXPO_ATLAS=true npx expo export` and inspect with `npx expo-atlas .expo/atlas.jsonl`. Check that no pipeline or Remotion code leaks into the app through workspace imports, consider zod/mini for the app-side schemas, and confirm no reel media sits in bundled assets. Try the experimental tree-shaking env vars only in M7. Profiling ladder: dev-menu perf monitor, then RN DevTools Profiler/Performance, then Instruments, Android Studio Profiler or Flashlight (Android) on the release build. _Why:_ JS size matters less on Hermes than what executes at startup, but the monorepo makes accidental heavy imports easy, and 119 reels at about 2 MB each (about 240 MB) must stay on the static host. Full tree shaking is still experimental, so it is a late optional step. zod.dev reports roughly 64-69% smaller gzipped output for zod/mini in its examples.

## Fact-check: changes to the recommendations

- FlashList: install @shopify/flash-list@2.3.3 explicitly (JS-only, runs in Expo Go) and list it under expo.install.exclude, instead of taking the SDK pin 2.0.2. Keep Reanimated 4.5.1 / worklets 0.10.1 / gesture-handler ~2.32.0 on the pins, since those have native code inside Expo Go.
- Frame budget: make 8.33 ms the primary budget on ProMotion iPhones in both Expo Go and the EAS build (both ship CADisableMinimumFrameDurationOnPhone = true). 16.67 ms applies only to 60 Hz devices. Drop the open question about Expo Go being capped at 60 fps.
- Expo Go plan: the 'everything runs in Expo Go' premise holds only until SDK 58 goes stable (beta window ends roughly 6-13 Oct 2026). Before then either turn off App Store auto-update for Expo Go 57.0.9 on tester iPhones, or bring the EAS development build forward from M7, or budget for `eas go --sdk-version 57` (paid Apple Developer account). Do not upgrade to SDK 58 mid-demo: it moves to RN 0.88 and React 19.3 and would invalidate the pinned versions in this track.
- Feed data shape (my reasoning, not source-verified): do not trim the head of the list to keep a 'small data window'. FlashList v2 has maintainVisibleContentPosition on by default, and removing items above the current page while pagingEnabled is set invites offset jumps. Keep the list append-only, let virtualisation bound what is mounted, and let the re-plan rule replace only the unplayed tail. Always pass keyExtractor.
- Feed fallback: react-native-pager-view 8.0.2 is bundled in Expo Go on SDK 57 and supports vertical paging; list it as the fallback ahead of FlatList windowSize 3 if recycling and player lifecycle conflict.
- Add expo-video specifics to the feed recommendation: surfaceType "textureView" on Android for full-screen cover-fit cells, strictly one VideoView per VideoPlayer, drop the poster on onFirstFrameRender, leave timeUpdateEventInterval at its default 0 and read currentTime at swipe end, and set useCaching: true so resurfaced review reels start from disk.
- Reanimated flags: since the scroll-flicker and synchronous-props flags are static and off in Expo Go, treat Expo Go animation results as a lower bound and re-measure in the EAS build with the flags set in package.json before judging jank.
- Agent budget: a Vitest bench in packages/agent runs on V8 with a JIT and will not predict Hermes V1 (interpreter only). Keep it as a regression guard and take the 2 ms p95 figure only from performance.measure on the phones in --no-dev mode.
- Poster and ThumbHash: scope this as a pipeline task (extract a first-frame poster and a hash, add both to the manifest schema). The reel folders have neither today; it fits inside the free re-render pass if the theme changes.
- Drop the zod/mini suggestion: saving is under 10 kb gzipped and it would fork the shared @reels/schemas contract.
- Startup numbers: quote Android hot start as 1 s (Play Console), keep cold 5 s / warm 2 s. Measure iOS launch on warm launches per Apple's guidance; Expo Go cannot give a valid startup number at all.

## Fact-check: what the track missed

- SDK 58 rollover risk: the App Store Expo Go will stop opening SDK 57 projects shortly after SDK 58 stable, likely during this demo's build period. The track left this as an open question; it is the largest schedule risk for iPhone testing.
- apps/mobile is still the blank template: no expo-router, no experiments block, userInterfaceStyle "light". For a dark app (#0B1220) set userInterfaceStyle to dark and a matching root/splash background, otherwise there is a white flash at launch and on screen transitions that reads as slow startup.
- Knowledge map rendering if the answer is a graph or hybrid rather than a 40-cell grid: Skia 2.6.2 and react-native-svg 15.15.4 are both in Expo Go on SDK 57. Compute node positions in the pipeline at build time rather than running a force layout on Hermes; 46 nodes and 60 visible edges (38 prerequisite, 22 related) are fine in SVG if only opacity and colour animate. The track only covered plain Views.
- Time-dependent states ("due for review", "locked") need a coarse `now` value in the store, updated at swipe end and on foreground. Calling Date.now() inside a selector or render breaks React Compiler purity rules and never triggers the re-render that makes a concept turn 'due'.
- Feed versus dashboard: Expo Router tabs keep the feed mounted. Pause and release preloaded players when the feed loses focus, or decoders keep running under the map screen and eat its frame budget and memory.
- Memory and decoder budget: 1 active plus 2-3 preloaded 720x1280 H.264 players. No number is proposed for peak RAM or player count; PLAN.md flags Android decoder limits but the track sets no budget or test.
- Measured reel-start latency: the 500 ms target has no instrumentation. Log swipe-settle to onFirstFrameRender, and agent ms per pick, into the existing JSONL event log so tester phones report it without a profiler.
- Persistence consistency: the event row and the learner-state snapshot should be written in one withExclusiveTransactionAsync call (withTransactionAsync does not isolate concurrent queries), otherwise a kill between the two leaves the map and the log disagreeing.
- Reel files already have faststart (moov before mdat, checked on rn-navigation--pitfall/video.mp4), so progressive start is fine; what is unchecked is the static host: range requests and cache headers decide whether the 500 ms target and useCaching work.

## Findings

### 1. Hermes V1 is the default engine on SDK 57 / RN 0.86, and the two Hermes V1 regressions that shipped with SDK 57 are fixed in the version the repo pins (expo ~57.0.26, RN 0.86.3).

SDK 57 changelog: the initial release inherited a Hermes V1 memory regression affecting apps that import react-native-worklets/reanimated, fixed in expo@57.0.9 (RN 0.86.2); a development-time startup regression was fixed in expo@57.0.17 (RN 0.86.3). RN 0.84 blog: Hermes V1 became default with better execution speed and lower memory. RN 0.82 blog (Expensify benchmark): total TTI 7.6% faster on low-end Android and 2.5% on iOS, bundle load 3.2% / 9% faster; Hermes V1 has no JIT or native compilation yet. apps/mobile/package.json pins expo ~57.0.26 and react-native 0.86.3.

Source: <https://expo.dev/changelog/sdk-57> · confidence: high · version-sensitive

### 2. Route-level lazy loading does nothing for native production startup: async routes are development-only on native, and release builds already ship precompiled Hermes bytecode that is loaded on demand.

Expo async-routes doc (modified 2026-09-18): on native, async routes are experimental, opt-in and supported only in development; native production builds load routes synchronously and Hermes apps gain little from splitting because bytecode is memory mapped. RN 'Optimizing JavaScript loading' doc: release builds compile JS to bytecode ahead of time; consider React.lazy for heavy screen-level components; Expo projects do not inline require calls by default. Expo Hermes guide: `npx expo export` and `eas update` produce Hermes bytecode bundles.

Source: <https://docs.expo.dev/router/web/async-routes/> · confidence: high · version-sensitive

### 3. Build-time font embedding (the recommended, zero-load-time strategy) and a faithful splash screen are not available in Expo Go; in Expo Go, fonts must be loaded at runtime or system fonts used.

Expo fonts guide: the expo-font config plugin makes fonts available immediately at app start with no async loading code, but does not work in Expo Go (needs a development build); the alternative is the useFonts hook at runtime. Variable fonts on native need SDK 58+. expo-splash-screen v57 doc: Expo Go shows the app icon instead of the splash, dev builds do not reflect all config, so test the splash on a release build; use preventAutoHideAsync() at module scope and hide() as soon as possible; default fade duration 400 ms.

Source: <https://docs.expo.dev/develop/user-interface/fonts/> · confidence: high · version-sensitive

### 4. React Compiler 1.0 is stable and is switched on in Expo with one app-config flag; the SDK 57 default template enables it, but this repo's apps/mobile/app.json does not yet.

Expo guide: set `"experiments": { "reactCompiler": true }` in app.json; Babel is preconfigured since SDK 54; compiler lint rules ship in eslint-config-expo since SDK 55; it only compiles app code (not node_modules); opt out per component with the 'use no memo' directive. The sdk-57 expo-template-default app.json has `reactCompiler: true`; the repo's app.json has no experiments block. react.dev 1.0 post: up to 12% better initial loads/navigations and some interactions over 2.5x faster at Meta, memory neutral. Reanimated docs: with the compiler, use sharedValue.get()/set() rather than .value.

Source: <https://docs.expo.dev/guides/react-compiler/> · confidence: high · version-sensitive

### 5. Zustand 5 (5.0.15) is built on React's native useSyncExternalStore, so re-renders are controlled entirely by selector output; selectors that return fresh objects or arrays cause loops.

Zustand v5 migration doc: React 18 is the minimum, use-sync-external-store is only a peer dependency for the 'traditional' equality-function API, a selector returning a new reference can cause infinite loops ('Maximum update depth exceeded'), and useShallow gives a stable reference. npm registry (checked 2026-10-04): zustand 5.0.15, jotai 3.0.1, @legendapp/state 2.1.15.

Source: <https://github.com/pmndrs/zustand/blob/main/docs/reference/migrations/migrating-to-v5.md> · confidence: high · version-sensitive

### 6. SDK 57 pins react-native-reanimated 4.5.1 with react-native-worklets 0.10.1. Reanimated's own guidance is CSS transitions/animations for state-driven changes, worklets for gesture/scroll-driven ones, and non-layout properties throughout; its static feature flags cannot be set in Expo Go.

Expo sdk-57 bundledNativeModules.json: reanimated 4.5.1, worklets 0.10.1, gesture-handler ~2.32.0. Reanimated performance guide: animating transform, opacity or backgroundColor is cheaper than layout-affecting styles; animate at most about 100 components on low-end Android and 500 on iOS; New Architecture regressions are mostly visible in development builds and much smaller in release; 120 fps on iOS needs CADisableMinimumFrameDurationOnPhone in Info.plist. Feature-flags doc: static flags are unsupported where Reanimated is prebuilt, such as Expo Go. Transition docs discourage transitionProperty 'all'. Reanimated 4 release post recommends the CSS API for state-controlled animations.

Source: <https://docs.swmansion.com/react-native-reanimated/docs/guides/performance/> · confidence: high · version-sensitive

### 7. FlashList v2 and Legend List are both JavaScript-only, so both work in Expo Go; FlashList v2 is New-Architecture-only, needs no size estimates, and is the version `expo install` picks on SDK 57 (2.0.2).

Shopify engineering post: v2 is a ground-up rewrite that removed all native code, relies on New Architecture synchronous layout measurement, and reports up to 50% less blank area while scrolling than v1. FlashList performance doc: assess only in release mode (it can look slower than FlatList in dev), never put `key` props inside item trees, use getItemType for mixed cell types. Legend List README: pure TypeScript with no native dependencies, recycling is opt-in via recycleItems (off by default). npm latest on 2026-10-04: @shopify/flash-list 2.3.3, @legendapp/list 3.6.0.

Source: <https://shopify.engineering/flashlist-v2> · confidence: high · version-sensitive

### 8. expo-sqlite (in Expo Go) covers both the event log and the learner state: async APIs for writes, synchronous APIs that block the JS thread, and a key-value store with synchronous getters/setters. The kv-store does not enable WAL itself.

expo-sqlite v57 doc: included in Expo Go; tip to enable WAL journal mode for general performance; prepared statements via prepareAsync/executeAsync; every *Sync method carries a note that heavy work blocks the JavaScript thread; `expo-sqlite/kv-store` is an AsyncStorage drop-in that adds setItemSync/getItemSync. sdk-57 Storage.ts source: each set is a single upsert statement and no journal_mode or synchronous pragma is issued. sqlite.org pragma doc: in WAL mode with synchronous=NORMAL most transactions perform no sync, the database stays consistent, but the last commits can roll back after power loss or an OS crash. No primary source gives millisecond write latencies.

Source: <https://docs.expo.dev/versions/v57.0.0/sdk/sqlite/> · confidence: high · version-sensitive

### 9. The new expo-file-system File API (in Expo Go) can append to a JSONL file, but its write call is synchronous on the JS thread.

expo-file-system v57 doc and sdk-57 File.types.ts: `file.write(content, options)` returns void (synchronous); FileWriteOptions has `append` (default false) and `encoding`; `file.open()` returns a FileHandle with synchronous writeBytes and an append mode (FileMode.Append = 'wa'); writableStream() also exists. The old promise-based API lives under `expo-file-system/legacy`.

Source: <https://docs.expo.dev/versions/v57.0.0/sdk/filesystem/> · confidence: high · version-sensitive

### 10. react-native-mmkv is at major version 4 (4.3.2), is a Nitro Module, and does not run in Expo Go.

MMKV README: V4 is a Nitro Module requiring RN 0.76+ and react-native-nitro-modules; Expo projects must install both and run `npx expo prebuild`; calls are fully synchronous and it claims roughly 30x AsyncStorage speed. npm registry: 4.3.2 with react-native-nitro-modules as a peer. It is absent from Expo's sdk-57 bundledNativeModules.json.

Source: <https://github.com/mrousavy/react-native-mmkv> · confidence: high · version-sensitive

### 11. expo-image (in Expo Go) has the pieces needed for instant reel posters: prefetch, memory+disk caching, hash placeholders and a recycling key.

expo-image v57 doc: built on SDWebImage and Glide; Image.prefetch(urls, { cachePolicy }) with prefetch default 'memory-disk'; cachePolicy options none/disk/memory/memory-disk; BlurHash and ThumbHash placeholders; `recyclingKey` resets content when a recycled view (FlashList is named) changes source; `transition` for cross-fades; `priority` for load ordering. SDK 57 added writeToCacheAsync/readFromCacheAsync.

Source: <https://docs.expo.dev/versions/v57.0.0/sdk/image/> · confidence: high · version-sensitive

### 12. In SDK 57, platform shaking and dev-code elimination are automatic in production bundles and ESM import support is on by default, but full unused-export tree shaking is still an experimental opt-in; Expo Atlas is the bundle analyser.

Expo tree-shaking guide: Platform.OS branches and **DEV**/NODE_ENV code are removed in production only; experimentalImportSupport is default since SDK 54; unused-export removal needs EXPO_UNSTABLE_METRO_OPTIMIZE_GRAPH=1 and EXPO_UNSTABLE_TREE_SHAKING=1 (production only, labelled experimental since SDK 52), works only on import/export syntax, and makes inlineRequires safe to enable. Analyzing-bundles guide: `EXPO_ATLAS=true npx expo start` (open with shift+m) or `EXPO_ATLAS=true npx expo export` then `npx expo-atlas .expo/atlas.jsonl`.

Source: <https://docs.expo.dev/guides/tree-shaking/> · confidence: high · version-sensitive

### 13. JS-level profiling works in Expo Go; native profilers and release-build JS profiling need a build. User Timing marks and PerformanceObserver are stable since RN 0.83 and also work in production.

RN DevTools doc: panels are Console, Sources, Network (0.83+), Performance (0.83+, showing JS execution, React performance tracks, network events and custom User Timings), Memory, React Components and React Profiler. RN 0.83 blog: performance.now, mark/measure, event timing and longtask entries are stable and PerformanceObserver works in production builds; Expo apps keep a separate 'Expo Network' panel without Performance-panel integration. Expo debugging doc: DevTools opens with `j` in dev clients or Expo Go; JS profiles work only in debug builds; use Xcode or Android Studio for native profiling; the dev-menu performance monitor shows UI and JS FPS. Flashlight README: Android only (iOS in progress), works on production apps. react-native-release-profiler README: Hermes sampling in release builds.

Source: <https://reactnative.dev/docs/react-native-devtools> · confidence: medium · version-sensitive

### 14. Dev mode is not representative, and the numeric targets the sources give are 16.67 ms per frame at 60 fps, Android's 'excessive' startup thresholds, and Apple's 400 ms to first frame.

RN performance doc: 60 fps leaves at most 16.67 ms per frame; JS thread performance suffers greatly in dev mode; console.log can bottleneck the JS thread in bundled apps; "Always make sure to test performance in release builds." Expo development-mode doc: disable dev mode for any performance test using `npx expo start --no-dev --minify`. RN 0.82 blog: Android debug builds ran animations at about 20 FPS versus about 60 FPS with the debugOptimized variant. Android vitals page: cold start of 5 s or more, warm 2 s or more, hot 1.5 s or more count as excessive (TTID). Apple WWDC19 session 423: aim to render the first frame within 400 ms and measure warm launches.

Source: <https://reactnative.dev/docs/performance> · confidence: high

## Open questions

- Does the RN DevTools Performance panel (tracing, added in RN 0.83) actually appear when connected to Expo Go on SDK 57? Expo's debugging doc lists Console, Sources, Network, Memory, Components and Profiler but not Performance. Check by pressing j on device.
- Expo Go on physical iPhones: expo.dev/go for SDK 57 points to the App Store, while the current setup doc says an Apple Developer Program subscription plus `npx eas-cli go` and TestFlight are required (possibly written for SDK 58 beta), with matching Expo account sign-in. Which applies to the testers' phones?
- Does Expo Go's Info.plist enable 120 Hz (CADisableMinimumFrameDurationOnPhone)? If not, Reanimated animations on ProMotion iPhones are capped at 60 fps in Expo Go and the frame budget differs from the eventual build.
- No primary source gives write latencies for expo-sqlite async inserts, kv-store setItemSync, or File.write append on phones. A 1,000-write micro-benchmark on the target devices in release mode is needed before fixing persistence budgets.
- What journal mode does expo-sqlite/kv-store end up in? The JS source issues no WAL or synchronous pragma; I did not read the native default.
- Real cost of the agent's next() on Hermes V1 (no JIT) is unmeasured; the 2 ms / 5 ms budgets are proposals. Does the re-plan rule call next() speculatively 2-3 times per swipe?
- How does FlashList v2 cell recycling interact with expo-video VideoView and manually created/released players? Unverified here; it decides between FlashList, FlatList or a hand-rolled 3-page pager.
- Is experimental Expo tree shaking (EXPO_UNSTABLE_TREE_SHAKING) reliable on SDK 57 with npm workspaces and Zod 4? Not tested.
