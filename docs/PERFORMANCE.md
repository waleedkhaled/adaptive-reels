Where a correction refuted or changed a recommendation, this plan follows the correction and says **Corrected**; a deliberate departure is marked as an owner decision. **Nothing here has been measured on a phone.** Every number is a target unless it says "measured" (measured = ffprobe/ffmpeg on the 119 rendered files on this Mac, by the research or, where it says today, re-run for this revision). `apps/mobile` is still the blank template, so sections 2 to 5 describe new code, not a retrofit.

## 2. Feed architecture

### 2.1 List

Core `FlatList` with native paging (already decided). A cell is full pager height and holds only a ground-colour `View` plus a `VideoView`, or a card body. Chrome (top row, reason strip, action row, tab bar) is mounted **once, outside the list**, over the reel's empty safe-zone bands, and does not scroll with the reel. ### 2.2 Player pool

```ts
function assign(slot: PlayerSlot, reel: ManifestReel | null, force = false) {
  const id = reel?.reel_id ?? null; // by reel id: the URI flips between https and file://
  if (slot.reelId === id && !force) return;
  const gen = ++slot.gen;
  slot.reelId = id;
  setLoaded(slot, null); // the cell drops its VideoView and shows the cover (2.3)
  slot.chain = slot.chain
    .then(() => (gen === slot.gen ? slot.player.replaceAsync(reel && sourceFor(reel)) : undefined))
    .then(() => void (gen === slot.gen && setLoaded(slot, id)))
    .catch((e) => onLoadError(slot, gen, e)); // clears slot.reelId if gen is current: retries pass
}
```

- **Keyed by video ordinal.** A reel slot carries `ordinal` k, its running count among reels (cards do not count), and uses `pool[k % POOL]`. Previous, current and next reel always hold three different players, with or without cards between them, and inserting or removing a card never invalidates a preloaded player. `POOL = 2` means current + next only; a back-swipe then loads from disk.
- **Serialised `replaceAsync` (Corrected, must on SDK 57):** one promise chain and a generation token per player; latest wins, stale requests are skipped. The iOS fix for overlapping source loads (#47967) is 58-only, and "a quick action re-plans N+1" creates exactly those overlaps. Never use the synchronous `replace()` (it blocks the iOS main thread). Retries (6.4) call `assign(slot, reel, true)`.
- **Play state** (full contract in 2.5): at activation pause the others, then `play()` the current player only if it already holds this reel (PLAN: "audio never overlaps"). Every paused player except the one whose impression is open is rewound to 0. **No autoplay** while a screen reader is running (UX 6.1): the reel waits at frame 0, which is empty ground, behind the Play control, and `playing_ms` runs from the tap. Under Reduce Motion alone reels autoplay, because the re-rendered reels only fade (DESIGN, UX 6.3; owner decision).
- Lifecycle: on Feed tab blur and app background, pause all players inside try/catch and do **not** release (open iOS issue #30994 with Expo Router); the open impression survives and playback resumes on return (2.6). Release only when the provider unmounts, `pause()` then `release()` (insurance; the release bug is fixed from 57.0.2). If M6 shows the map paying for idle decoders, `assign(slot, null)` the two non-current players on blur. On SDK 57 a detached `VideoView` keeps a strong reference to its player (#46453, fixed in 58), which can skew the memory-drift number.

A re-pointed player therefore always gets a new mount with a fresh cover and no stale frame can show. - The cover uses a `ground.video` token: default `bg.base`, overridable per platform if a decoder shifts the colour. The ground must survive BT.709 limited-range 8-bit encoding; DESIGN's `#181612` is an exact fixed point (recomputed here; `#101618`, for comparison, decodes to `#101617`).
- **Buffering** (DESIGN's indicator after 400 ms) is defined as: the reel is active, `play()` was requested, and for 400 ms either playback has not started (`playing_ms` not yet logged) or, mid-reel, `status` is `loading`.

### 2.4 Source, caching, buffer

**Decision: file-first, one disk mechanism (Corrected: the research used two at once).** `sourceFor(reel)` returns `{ uri, contentType: 'progressive', useCaching: false }`. `uri` is the `file://` copy if `Paths.cache/reels/<reel_id>.<sha12>.mp4` exists with `size === manifest.bytes`; otherwise the HTTPS URL, streamed and not cached, while the file download is queued (6.4). The check is two synchronous file-system calls, one more reason `assign` runs at settle and not mid-swipe.

Why not `useCaching: true`, which tracks 06 to 08 recommended: (1) App Store Expo Go 57.0.9 was released on 2 Sep and the two iOS cache crash fixes shipped in expo-video 57.0.5 on 24 Sep, so the iPhone binary cannot contain them (my inference from the dates); (2) the iOS cache has a hard-coded 5 s request timeout, rejects responses that are not `video/*` or lack `Content-Length`, and keys on the URL with no revalidation; (3) a local file is the simplest playback path on both platforms and makes pre-downloading and source logging trivial. Unmeasured: start time from `file://`. M3 A/Bs file-first against URL + `useCaching`; because of (1) the iOS arm runs only in the EAS development build. **Keep rule:** switch to `useCaching` only if `playing_ms` p50 improves by at least 100 ms with zero player errors over 60 swipes on both platforms; otherwise file-first stays. A switch brings back the constraints in (2) and needs `clearVideoCacheAsync()` on a manifest version bump.

### 2.5 Agent-to-player contract

Two moments (2.1): **activation** changes play state only; **settle** does accounting, agent work, source loads and the pager lock. Slot states: played, active, **committed** (the next unplayed _reel_: assigned to a player, replaced only by an explicit action) and **provisional** (every other unplayed slot, cards included: re-planned freely). A card has no ordinal and no player, so placing one directly after the active item, ahead of the committed reel, costs no player work. Pinning the next _slot_ instead, as the first draft did, pushed a due review behind one more whole reel: about 123 s after the answer on the demo clock with 30 s reels watched in full, outside PLAN M5's 60 to 120 s.

- **Re-plan** (pure; 3 to 5 `next()` calls): drop the provisional slots; start `planState` from `learner` with a fresh `now`; call `next()` until it returns a reel. Each card before that (at most 2) goes directly after the active item. Two more calls give the provisional slots. Then the three `assign` calls run again for the anchor reel: no-ops unless the next reel changed.
- **Two agent states.** `learner` is persisted and advances only through things that happened: `shown(slot)` at settle (history, cadence count; no RNG step: every draw is keyed by the seed, the reel or card ordinal and its purpose, UX section 9 item 3, so an inserted card cannot shift a later reel pick), `reel_end` signals, a quick action or its Undo, an answer, "Later". `planState` lives inside one re-plan and is then thrown away, so a snapshot never holds a reel that was planned but not shown, and a re-plan repeats the same picks unless `learner` or what is due has changed. `@reels/agent` must export `shown()`, the same pure reducer `next()` uses to build `state'`.
- Cards: when a card for concept c is planned, queue the download of c's reteach reel so the wrong-answer path does not start cold. A card passed by a second flick before it settles was never shown: log `card_deferred` and treat it as "Later" (UX 3.3).
- Tail edits touch only unplayed slots above the highest settled index, and wait while the list moves: from `onScrollBeginDrag` or a `scrollToIndex` call until the next `onSettle` callback, with a 600 ms timeout after `onScrollEndDrag` for a drag that never left the page. If the learner reaches a reel that is not loaded (a flick onto a provisional reel, a re-plan still loading, back by two), the cell shows the cover until the first frame and the start is logged as not preloaded. Do not build "after the swipe" work on `InteractionManager` (removed in SDK 58); run it from `onSettle` or `requestIdleCallback`.

### 2.6 Loop and watch signals

- **Corrected:** `loop = true`. The research's `loop = false` with `playToEnd` as the completion signal conflicts with PLAN's signals; `playToEnd` fires on every loop on both platforms. After 2 loops with no input the player is paused (UX 3.2).
- Per impression (opened and closed only at settle, 2.5): `loops` = `playToEnd` count; `played_ms` = time with `playing` true, summed from `playingChange` events. At close, before the rewind, `t = player.currentTime`. If `loops === 0`, `t < 1` and `played_ms > 0.9 * duration_ms`, count one loop: `playToEnd` reaches JS asynchronously and the loop point is where people swipe. Then `watched_ms = loops * duration_ms + t * 1000`, with `duration_ms` = the manifest's `duration_s * 1000`.
- `outcome` (schema enum), first match: `completed` when `watched_ms >= 0.9 * duration_ms`; `early_skip` when `loops === 0` and `t * 1000 < min(0.25 * duration_ms, 5000)`; otherwise `partial`. Rewatch (`watched_ms >= 1.5 * duration_ms`) replaces the Completed interest signal, never adds to it; the logged outcome stays `completed`. All position-based: paused time does not count and no `timeUpdate` events are needed. A peek (past 60%, back before settle) opens no impression: nothing is logged, no interest changes, and it cannot count toward "two early skips".
- App background and Feed blur only pause: the impression stays open, the position is kept, and playback resumes on return unless the learner had paused. `reel_end` is written at the next settle. The background flush stores `{ slot, loops, t, played_ms }` in the snapshot; after a kill the next launch writes the missing `reel_end` from it with `ended_by: 'blur'` (UX 8).

One Zustand 5 store (5.0.15, JS-only) is the in-memory source of truth; one expo-sqlite database is the disk copy. No MMKV (Nitro, not in Expo Go), no kv-store sync setters, no `File.write` append (both block the JS thread).

- A selector never returns a fresh object or array (Zustand 5 then loops with "Maximum update depth exceeded"). Result: an activation re-renders two cells plus the chrome; an answer re-renders one tile, its rail row and the counts.

No `Date.now()` in a selector or in render: it breaks React Compiler purity and never triggers the re-render that turns a tile "due". At most one ticking countdown on screen, a leaf component with its own 1 Hz state.
- Playback position, progress and watch time never enter React state: player events go to refs or shared values and reach the store only at settle.

**expo-sqlite setup** (in Expo Go). One startup path, all synchronous and before the first render: `openDatabaseSync`, then `execSync` with `PRAGMA journal_mode = WAL; PRAGMA synchronous = NORMAL;` and both `CREATE TABLE IF NOT EXISTS` statements, then `getFirstSync` for the snapshot (with NORMAL the last commits can be lost on power loss, not on an app kill; acceptable for a demo). Tables, every column `NOT NULL`: `events (seq INTEGER PRIMARY KEY AUTOINCREMENT, at INTEGER, session_id TEXT, type TEXT, json TEXT)` and `snapshot (id INTEGER PRIMARY KEY CHECK (id = 1), schema_version INTEGER, updated_at INTEGER, json TEXT)`. Every write, awaited or not, is enqueued on one promise chain: order is preserved and nothing touches the main handle while a transaction is open (per the v57 docs such a write aborts with `database is locked`). Inside a transaction use its own handle (`txn.runAsync`), never a statement prepared on `db`.

| What                                      | Property                                    | Mechanism                                                                                                                                                                                                                            | Thread      |

| State colours (tile, answer row, tag)     | `backgroundColor`, `borderColor`, `opacity` | Reanimated CSS transition with explicit `transitionProperty`, never `all`                                                                                                                                                            | UI          |
| Tile fill                                 | `transform: scaleY` from the bottom edge    | 450 ms timing                                                                                                                                                                                                                        | UI          |

1. Only `transform`, `opacity`, `backgroundColor` and `borderColor` animate. Never height, width, margins or flex; panels are fixed-height views moved by `translateY`. No blur, glass, shadow or gradient layers (design direction), so chrome is opaque views.
2. One mechanism per property per view. Under 100 animated views mounted per screen (Reanimated's low-end Android guidance); count them on the map in M6. Nothing loops or pulses: while a reel plays, the progress line is the only running animation.
3. At activation (60% visible, mid-swipe) our only JS is `setActive` (one store write: two cells and the chrome re-render), play / pause / rewind on players that are already loaded, and the start-of-playback poll (section 1, 2.3). The impression log, `assign`, the agent, every other store write and all SQL run at settle. A source load on SDK 57 still costs iOS main-thread time (#47975 is 58-only), so it stays out of the window the frame budget measures; the price is that the next reel starts preloading about 200 ms later, on a 24 to 37 s reel. FlatList's own per-event scroll bookkeeping (it sets `scrollEventThrottle` to 0.0001) is JS we do not control.
4. React Compiler is on from day one: `sv.get()` / `sv.set()`, never `.value`; no hand-written `useMemo` or `memo` by default.
5. Reduce Motion: one store value from `AccessibilityInfo.isReduceMotionEnabled()` and `reduceMotionChanged` drives everything (DESIGN.md, Motion): every `withSpring` and `withTiming` gets `reduceMotion: rm ? ReduceMotion.Always : ReduceMotion.Never`, never the default `ReduceMotion.System` (read once at start, like `useReducedMotion`), and CSS durations follow the same value. Reels still autoplay (2.2). Check the setting on the demo phone or the key beats will not animate.
6. **Expo Go limit:** Reanimated 4.5.1 is prebuilt there, so static flags are frozen at their defaults: `ENABLE_SHARED_ELEMENT_TRANSITIONS` off, `ANDROID_` and `IOS_SYNCHRONOUSLY_UPDATE_UI_PROPS` off, `DISABLE_COMMIT_PAUSING_MECHANISM` off, SVG CSS animations on. Nothing may depend on a non-default flag (R4).

### 6.3 Hosting, headers, URLs

- Development and the Expo Go demo: `pipeline/src/serve.ts` on the LAN or a hotspot plus a warmed device; it already sends 206, `Content-Range`, `Content-Length` and `video/mp4`. Tester build: HTTPS only. Cloudflare R2 with a custom domain if the owner has a domain on Cloudflare (the free tier covers it; `r2.dev` is rate-limited and uncached); otherwise Bunny ($1 per month minimum) or the CloudFront free flat-rate plan. **Owner decision.**
- Required on every reel response: `Content-Type: video/mp4` (set it explicitly on upload; tools default to `application/octet-stream`), `Accept-Ranges: bytes` with 206 on ranges, a real `Content-Length` (never chunked), `Cache-Control: public, max-age=31536000, immutable`. Manifest: `Cache-Control: public, max-age=60`. No on-the-fly transformation of MP4s. Check each host with `curl -sI <url>` and `curl -s --range 0-99 <url> -o /dev/null -w '%{http_code} %{size_download}\n'` (expect `206 100`).
- **Corrected:** the "one hostname for HTTP/2 reuse" advice is dropped. expo-video builds a new OkHttp client per source on Android and a new URLSession per cached asset on iOS, so every cold reel pays a full handshake. Preloading is mandatory, and edge distance matters more than protocol version.
- **Content-hashed URLs:** `reels/<reel_id>.<sha256[0:12]>.mp4`, in development too. **Corrected reason:** device caches never revalidate (expo-video's iOS cache key is the URL string; our file cache uses the file name), so a re-render under an old URL plays stale or mixed bytes. `Cache-Control` only affects the CDN edge, and the dev server's `no-cache` does not protect the phone.

### 6.4 Prefetch rules

1. Memory: the pool holds previous, current and next reel, re-asserted by the three `assign` calls at every settle (2.5). Nothing else is buffered in a player.
2. Disk queue with expo-file-system (`File.downloadFileAsync` into `Paths.cache/reels/`), 2 at a time, in this order: committed reel if missing, provisional reels, reteach reel of a planned card, top candidate of each other pool, then (Wi-Fi, idle) the rest of the picked topics.
3. **Corrected:** check `file.exists` first (`idempotent: true` overwrites, the default throws). Download to `<name>.part`, check `size === manifest.bytes`, then `move` into place, so a truncated file is never played.
4. Player `status === 'error'`, a rejected `replaceAsync`, or no playback 5 s after the reel settled (UX 3.9, `cause: timeout`): for a file source delete the file and `assign(slot, reel, true)`, which now resolves to the URL; for a URL retry the same way once after 1 s, then show the offline state (M7) and log `reel_load_failed`.
5. Before a demo (**Corrected:** raised from could to should): pre-download the picked topics on Wi-Fi, rehearse once in airplane mode and once on cellular. The OS can purge `Paths.cache` when storage is low, so rehearse on the day.

## 10. Measured results

Measured 2026-10-05 in the iOS Simulator (iPhone 17 Pro) on a Mac, in Expo Go, with production-mode JS (`npx expo start --no-dev --minify`), reels playing from their offline copies. One session of 30 reels at about 4 s each, cards set aside with "Later". This is not a phone: the simulator runs on the Mac's CPU and GPU, so the numbers show the code path is fast, not what a mid-range phone does. Device runs are still open (section 8).

| Budget (section 1)                       | Measured                                 | Pass line        |
| ---------------------------------------- | ---------------------------------------- | ---------------- |
| Reel start, `playing_ms` p50 / p95       | 194 ms / 198 ms over 30 starts           | p95 under 500 ms |
| Preload hit rate (`ready_at_activation`) | 29 of 30 (97%)                           | 90%              |
| Stall reloads, load failures             | 0, 0                                     | n/a              |
| Frame-rate proxy (`hz`)                  | 60 on every start                        | n/a              |
| Event log                                | 123 events, all valid against the schema | n/a              |

The same measurement in development mode gave a p95 of 470 ms. Reproduce it with `npm run analyze -- <exported log>`.

What produces these numbers:

- A `FlatList` pager with `getItemLayout`, `pagingEnabled` and `windowSize` 5 (section 2.1).
- A pool of 3 `expo-video` players keyed by `ordinal % 3`, so the next reel loads into an idle player while the current one plays and no player is created during a swipe (2.2).
- Activation at 60% visible only switches play state; agent calls, logging, source loads and SQLite writes wait for the settle at 95% visible for 100 ms (4).
- The feed's chrome is mounted once outside the list, the progress line animates on the UI thread with Reanimated, store reads go through atomic Zustand selectors, and React Compiler is on (3, 4).
- File-first playback: saved copies play without the network (29 of 30 starts came from disk).

Specified above but not implemented yet:

- Events in the schema the app never logs: `swipe_frames` (the frame meter), `agent_next`, `replan_ready`, `map_cell_tapped` and `map_topic_selected`.
- Writing the missing `reel_end` after the app was killed, exclusive transactions, and the 1 s snapshot throttle (section 3).
- The stall watchdog (2.3) runs on iOS as well, not only on Android.
